# 서버 배지 지급 운영 절차 (v2.1)

지급은 Spring 서버와 MySQL에서 수행한다. 대화 세션, AI 호출, 회원 JWT, 로그인이나 관리자 API 호출이 필요 없다. 기본값은 OFF다. 이번 검토는 운영 조회와 로컬 쓰기 테스트만 수행했다.

## 켜기와 끄기

1. 운영 배포 전에 운영 MySQL 8의 읽기 전용 세션에서 `python tools/badges/member_badge_report.py --sql`이 출력하는 SQL을 실행해 예상치를 보관한다. 여기에는 회원별 내부 ID가 있으므로 결과는 외부 공유하지 않는다.
2. 실제 도입 시에만 `deploy/sql/automatic-badge-grant.mysql.sql`을 한 번 적용한다. 그 다음 새 서버 버전을 **모든 인스턴스에** 설정과 함께 재시작한다. 앱 시작 시 스키마를 확인한다. ON일 때 필수 지급 테이블이나 잠금 행이 없으면 시작에 실패한다. 기존 기록증·개인 기록·러닝 테이블은 사전에 설치되어 있어야 한다.
3. **ON**: `RIKU_BADGES_AUTO_GRANT_ENABLED=true`. 첫 회부터 모든 활성 회원의 전체 보관 이력을 집계하며, 이후에는 기본 5분 간격이다. 간격은 `RIKU_BADGES_AUTO_GRANT_DELAY_MS`로 지정한다. 단계별 조건을 모두 평가하므로 최초에 여러 단계를 함께 받을 수 있다.
4. **OFF**: 같은 변수를 `false`로 바꾸고 모든 지급 서버를 재시작한다. 신규 자동 지급만 멈춘다. 지급 원장과 이미 받은 배지는 유지된다. 다시 켜면 중단 기간에 남은 활동도 재검사한다. OFF 이후에도 저장된 활동을 삭제할 때 복원 근거와 학기 시작일은 유지한다. 아직 스키마를 설치하지 않은 기존 서비스는 종전 조회를 사용한다.
5. **대조**: 설치 후 `member_badge_report.py --audit-sql`은 읽기 전용 합계 쿼리를 출력한다. 배치 완료 후 `missing_grants`와 `awaiting_settlement`가 0인지 본다. `differs_from_frozen_result`는 사후 정정으로 달라진 이미 확정된 순위다. 필요 시 `--sql --with-ledger` 결과를 mysql --batch로 저장해 `--input <tsv>`로 내부 회원별 보고서를 만든다.

## 누락과 중복 처리

- 17계열 77종의 원본은 `src/main/resources/badges/series.json`. 비교 HTML을 생성할 때 프론트의 목록과 동등한지 검사한다. 활성 계정 전체에서 자격을 대조한다. 비활성 회원은 지급하지 않고 복귀하면 남은 근거로 다시 계산한다. 로그인이나 화면 조회는 지급 경로가 아니다.
- 일반 지급 작업은 DB 잠금으로 여러 서버의 동시 집계를 직렬화한다. 회원·배지 고유 키로 재시작과 재실행을 견디며 최초 지급 시각을 보존한다. 실패한 트랜잭션은 전부 취소되고 다음 실행에서 재집계한다. 운영진 수동 수여는 기존 별도 원장에 둔다.
- 출석은 한 회원의 마감된 모임당 한 번. 클럽 마일리지는 현행 그룹 거리를 우선하고, 같은 런·같은 그룹의 옛 페이서 거리가 모두 같은 양의 km인 경우에만 복원한다. 어느 그룹인지 모르거나 값이 모순되면 거리를 만들지 않는다.
- 개인 기록 삭제 전 최대 누적 거리, 기록증 삭제 시 보관 사실을 같은 트랜잭션에 기록한다. 이 근거는 배지 시스템 도입 이후부터 남길 수 있다. 도입 전에 제거된 데이터·이미지가 없는 과거 다운로드는 복원하지 않는다.
- 월간 개인 최고는 등급별 한 번, 월간·학기 입상은 각 기간별 공동 1~3위. 서울 시간 기준 마감된 기간만 처리하고 월간은 양수 득점자 20명 이상이어야 한다. 학기는 고정 월을 추정하지 않고 다음 공식 시즌 시작일로 마감한다. 서버가 본 `season.start-date`는 OFF 중에도 보존한다. 서버가 보지 못한 과거 공식 시작일은 `badges/semester-starts.txt`로 보완한다.
- 입상 자격자가 없는 기간은 다시 평가한다. 입상자가 있는 기간은 기간별 잠금 안에서 원장 기록과 확정을 함께 처리하며, 이후 점수 정정으로 이미 발급한 배지를 바꾸지 않는다. 일반 배지도 자동 회수하지 않는다.

## 검증

`BadgeMysqlIntegrationTest`는 전용 빈 MySQL 8에서 DDL, 77종 지급, 비활성·복귀, OFF/ON, 실패 후 재시도, 동시 지급, 과거 그룹 거리, 월간·학기 입상, 학기 변경 이력을 실제 SQL로 검증한다. 로컬 루프백만 접속한다. 테스트 계정 `badge_test`, 빈 DB `riku_badge_test` (또는 `RIKU_BADGE_TEST_DB=riku_badge_test_<숫자>`), `RIKU_BADGE_TEST_PORT`와 `RIKU_BADGE_TEST_PASSWORD`를 지정하고 Gradle test를 실행한다. 운영 DB를 사용하지 않는다.

## 도감 변경과 공개 범위

v2.1은 이번 검토 기준이다. 이름·그림 변경은 기존 코드를 유지한다. 종료할 단계는 양쪽 도감에서 제외한다. 원장에는 발급 당시 이름·조건·출처가 남아 종료 후에도 조회된다. 목표를 바꾸면 현재 코드가 목표값을 포함하므로 새 단계로 취급된다. 동일 단계로 이전할 의도라면 별도 코드 매핑과 중복 검증을 먼저 한다.

회원 간 프로필에는 활성 회원의 이름, 실제 지급된 도감 배지와 확정 입상만 제공한다. 수동 수여 메모·미획득 진행도·개인 기록은 공개하지 않는다. 설치 전/지급 전에도 프로필은 열리며 지급 내역은 비어 있다.
